## Directory-size rule: limits and mitigations

**The rule.** The owner's global coding rules (rule 2, Miller's law) allow at
most 9 files per directory.

**Why it cannot hold everywhere.** The spec fixes some layouts that exceed it:

| Place | Why it exceeds 9 | Limit it creates |
| --- | --- | --- |
| Repo root | The spec's layout lists about 16 entries (README, dotfiles, 8 folders, requirements) | Root is crowded; nothing else may be added there without a decision |
| `concepts/`, `problems/`, `discussions/` | One file per item, unbounded by design | Browsing by eye gets harder as the library grows |
| `tests/fixtures/` | One failing fixture per rule D1-D20 | 20 fixtures would not fit in one folder |

**Mitigations.**

1. **Code directories obey the rule.** `ci/dsa_lib/` holds 9 files and its
   rule implementations live in the `ci/dsa_lib/checks/` subpackage (7 files).
   `tests/` stays at or under 9 files.
2. **Fixtures are grouped by rule family**, so no fixtures folder exceeds 9:
   `tests/fixtures/structure/` (D1-D4, D8, D9, D14), `links/` (D5-D7, D10-D13),
   `policy/` (D15-D20), plus `valid/`.
3. **Content folders are exempt data directories.** Navigation is by the
   generated `api/v1/search.json` and `index.json`, not by listing the folder.
   If a folder passes about 500 files, revisit this decision (the spec makes
   slugs equal to filenames, so sharding would mean a spec change).
4. **The root is frozen** at the spec's list. New top-level files need a new
   entry in this log.

**Limits that remain.** A reader listing `concepts/` sees a long flat list;
the tooling is the intended way in. The rule is broken knowingly in these
places under the global rule 6 (the spec's layout outranks a readability
rule); each exempt directory carries a note in `README.md`.
